# 4.5 — Performance verification (US-51)

Date: 2026-11-08 · App: `apps/frontend` (Next.js 16.4.3, Turbopack) · Runtime for timings:
local `next dev --port 3110` with local Miniflare D1 (`E2E_LOCAL_DB=1`), no network
throttling. **Local dev is not 4G and not a Cloudflare preview — the 4G p95 budgets are
not claimed met from these numbers.**

## 1. pdf.js loads only on the import page (dynamic import)

- `src/app/dashboard/imports/import-flow.tsx:396-397` — `await import("pdfjs-dist")` and
  `await import("pdfjs-dist/build/pdf.worker.min.mjs")` inside `pdfText()`, which runs
  only in the PDF branch after a file is chosen.
- Only importer of the module in `src/`: `grep 'from "pdfjs-dist|require\("pdfjs-dist'` → 0 matches.
- `src/app/layout.tsx` imports only `next/font/google` and `globals.css`; nothing in the
  root layout reaches `import-flow.tsx` (the page imports it, `imports/page.tsx:15`).
- Production build (`E2E_LOCAL_DB=1 npx next build`, 23 pages, compiled in 12.1 s):

  | Asset | Raw | gzip |
  |---|---|---|
  | Root initial JS (4 `rootMainFiles`) | 433,518 B | 128,152 B |
  | `/dashboard/imports` flow chunk `29g1_bpo4281t.js` | 29,001 B | 9,521 B |
  | pdf.js main `2cy-r2a15m7d-.js` (lazy) | 469,770 B | 139,894 B |
  | pdf.js worker `2qciw4s-hp_1p.js` (lazy) | 1,189,195 B | 366,701 B |

- The two pdf.js chunks are the only chunks matching pdf.js internals
  (`PDFDocumentLoadingTask|GlobalWorkerOptions|pdfjsWorker`). Their names appear in
  **no** entry of `.next/build-manifest.json` (root main files or page chunk groups) and
  in **no** prerendered `.next/server/**/*.html` — they exist only as dynamic chunks.
- 4G caveat: picking a PDF downloads ~507 KB gzip of pdf.js (0.4–0.8 s at 5–10 Mbps) and
  parses it on the main thread before extraction starts. That is the main risk to the
  import-flow 5 s budget; it does not affect the dashboard or any other page.

## 2. Ledger is server-paginated (never 5,000 rows in the DOM)

- `src/lib/ledger/list.ts:59` — `LEDGER_PAGE_SIZE = 50`.
- `src/lib/ledger/list.ts:118-119` — `.limit(LEDGER_PAGE_SIZE).offset((page-1)*50)`; the
  count is a separate SQL `count()` (`:120`), not a fetched-then-sliced array.
- `src/app/dashboard/transaksi/page.tsx:259` renders only `ledger.rows`; `?page=` is URL state.
- Verified end-to-end: after a 60-row import, `/dashboard/transaksi` HTML contained
  50 body `<tr>` (limit) and the label `1–50 dari 60 transaksi`.
- Non-rendering exception: `src/lib/ledger/export.ts:28-41` reads every row of one
  workspace — that is the paid CSV export (file download, no DOM), by design.

## 3. Local timings (local dev only)

Method: a throwaway Node script signed up, created a workspace, granted the local
entitlement (to pass the free-tier gate), imported a 60-row one-month statement, then
timed HTTP requests with `performance.now()` until the full body was read. 3 warm-up
requests before each measurement (dev compiles a route on first hit); 12 dashboard GETs,
5 fresh-row import POSTs.

| Measurement | Min | Median | Max |
|---|---|---|---|
| Dashboard `GET /dashboard` total (108,081 B HTML) | 887.9 ms | **1,084.7 ms** | 2,810.5 ms |
| Dashboard TTFB | 111 ms | 146.4 ms | 1,018.7 ms |
| Import `POST /api/workspaces/{id}/imports`, 60 new rows (inserted 60, duplicates 0) | 516.5 ms | **574.7 ms** | 590.2 ms |
| Import POST, 60 duplicate rows (no-op batch) | 727.1 ms | 842.8 ms | 1,087.3 ms |
| First import of the run (includes route compile) | — | — | 1,839.8 ms |

Structure behind the numbers:
- Dashboard = one `Promise.all` of 10 SQL aggregates + `.limit(5)` recent rows
  (`src/app/dashboard/dashboard-content.tsx:66-191`) plus one flagged-imports read
  (`src/lib/ledger/trusted.ts:18`). No per-row query, no full-row fetch.
- Import = validate → gate → rate limit → reconcile → one `db.batch()` for the import row
  and its 60 transaction rows (`src/lib/imports/service.ts:73-94`). The 5 s budget also
  includes client-side parsing, which this probe does not measure.
